# 2026-11-10 决策输入对照实验

精简输入减少了 token，但本批测试没有证明决策质量稳定提升。保留当前线上提示词；实验版规则与示例 seed 仅位于 evals。另发现并修复了一个确定的 SQLite 交互检索错误：把“岿然不动”中的“不动”误认为独立状态，插入无关的格挡翻倍说明。

## 输入和实验边界

从两份真实会话固定20个完整局面，12个开发局面、8个留出局面；本次付费测试其中4个开发题、4个留出题，每题每版本一次。评分说明保存在快照中，但不发送给模型。实验开始后未根据留出结果修改提示词或示例。

- 当前版本：现有系统规则、整个 sts2-decider skill、战斗比较指令、检索证据。
- 精简版本：一份简短的运行规则，删去离线脚本说明；用独立文件中的数字对比示例替换同ID的 seed。
- 两版本共享同一局面的完整状态、候选、SQLite事实和向量攻略原文及ID，使用同一个现有单张攻击计算器。没有删数据库或重建向量库。
- 实际调用链为 SeedInjectingRetriever → SqliteFactsRetriever → ChromaRetriever。top_k=6，seed不占名额；向量匹配经过元数据过滤，并非每个局面都会有向量结果。审计清单记录每题来源和ID。
- 沿用 .env 中已配置的 DeepSeek 模型，thinking=disabled，输出上限1600。每次决策最多2次请求，禁用SDK自动重试；全实验最多32次请求、160000 token。请求前用输入UTF-8字节数加输出上限保守预留预算；失败或缺少usage时保留预留额。
- 两种顺序交替运行；没有游戏操作、程序战术替换或自动修改模型原始结论。

普通模式的本批结果不能推断思考模式、其他模型或平均楼层。当前版本前缀缓存更热，耗时和实际费用不是完全公平的比较。

## API 实测

| 指标 | 当前版本 | 精简版本 |
|---|---:|---:|
| 返回决策 | 8/8 | 8/8 |
| API请求 | 11 | 11 |
| 输入token | 60,370 | 45,328 |
| 输出token | 3,070 | 2,785 |
| 总token | 63,440 | 48,113 |
| 缓存命中输入 | 37,248 | 6,656 |
| 累计耗时 | 23.147秒 | 21.638秒 |
| 平均每题耗时 | 2.89秒 | 2.70秒 |
| 工具调用 / 返回未知 | 7 / 3 | 6 / 4 |

合计22次请求，111,553 token。精简版总token少24.2%，耗时少6.5%。但精简版缓存未命中的输入更多（38,672对23,122），不能据总token下降宣称实际账单下降。

首次沙箱内尝试发生连接错误，没有模型响应。随后获得网络执行权限，重新在独立文件中完成上述测试；连接失败文件保留，不计入决策质量。脚本现会在无模型响应的连接失败或预算不足时停止，并报告缺失配对。

## 人工检查原始回答

| 局面 | 当前版本 | 精简版本 |
|---|---|---|
| 3能量、敌人不攻击 | 理由把痛击加两打击算26伤，实际需4费；与提交计划不一致 | 首张可执行，仍未完整比较两种方案 |
| 1费、敌攻23 | 算对攻击伤害和防御省5血，仍缺少换血收益依据 | 同选攻击，用挡不住23解释5盾价值低；没有解决问题 |
| 四虫群战 | 原始计划三张牌都打同一强化虫，第二张后目标已死；理由却说重创另一只 | 明确声称12伤击杀18血；实际三张牌分散后没有击杀 |
| 恶魔之焰选牌 | 偏向稀有消耗核心 | 改选铁斩波补防御；理由更具体，但不能证明选牌最优 |
| 0能量、0费斩杀 | 正确击杀8血攻击甲虫，避免7伤 | 第一动作同样正确；工具返回未知，警告对显示伤害又产生疑虑 |
| 18血敌人、免费愤怒 | 两张已够斩杀，原始计划还继续攻击死目标 | 两张已够斩杀，原始计划仍安排战后防御 |
| 首领第一回合 | 坚毅7加增强邪眼16应为23盾，写成16；随机消耗后未停 | 3能量规划4张1费牌，明显超费 |
| 30盾选牌 | 选挑衅 | 选岿然不动；都有可讨论理由，不能把不同选牌直接算错 |

这里检查的是模型提出的完整计划与理由。执行程序仍会逐步观察并截断无法验证的后续步骤，不表示这些错误序列已经被实际执行。所有第一动作ID都来自合法候选；合法首步不等于整段计划正确。

现有计划检查器遇到未支持机制会提前返回，因此自动资源检查0报错也不能表示后续一定合法。报告保留原始计划、可检查前缀、模拟能力边界、原始回复和工具参数，人工复核再检查后缀。没有把未评分题或未知机制算作正确答案。逐条评语另存为 evals/fixtures/prompt_review_20261110.jsonl。

## 已应用的检索修复

旧逻辑对整份上下文做子串匹配：存在“岿然不动”就命中页面“不动”，把交互27、28、29放进前排。这些规则讲格挡翻倍，但局面实际没有该状态。

修复将完整实体名称精确匹配；再将长实体名称从文本中遮去，匹配说明中独立提及的效果。升级牌仍匹配其基础牌名；真实的“不动”状态或说明中的“获得不动”仍可检索。没有维护手工黑名单。

使用同一批20个快照、固定向量结果，仅重跑SQLite与seed组合，4个局面的这三条误匹配均消失：

- 30盾选牌：腾出位置后，实际进入证据的是岿然不动、铁斩波、挑衅的卡牌事实。
- 首领开场和已有足额格挡的局面：进入燃烧之血、永冻、药水套的实际遗物事实。
- 留出休息点：进入遗漏的遗物等事实。

此修复在API对照结束后实施；未重写冻结证据，也未追加付费调用。已证明修正检索内容，尚未证明改善游戏成绩。

验证：相关72项unittest全部通过，覆盖远程响应、计划、计算器、seed、SQLite和实验预算；git diff --check未报告空白错误。新回归先复现“短状态名命中长牌名”的失败，再验证真实状态、描述引用和升级牌基础名仍能正确检索。

## 下一步依据

1. 数据库确实被使用，但错误匹配会把无关事实推给模型；检索相关性比继续扩大知识量更值得检查。
2. 单张计算器能纠正受支持的数值，但当前遗物/状态的保守限制使7/13次工具调用返回未知。下一步应按独立机制逐项验证支持范围，不能直接忽略所有遗物。
3. 简短指令和示例未消除普通模式的基础计算与计划错误。继续增加原则前，使用本次固定题集比较推理配置或模型更有判断依据。
